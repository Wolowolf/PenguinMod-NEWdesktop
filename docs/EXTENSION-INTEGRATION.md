# EXTENSION-INTEGRATION.md — how the shipped extensions are integrated into the engine

Was `EXTENSION-ROADMAP.md` until Session 128: the plan (steps 1–6, Sessions 105–128) is finished, and this file is now the reference for how each mechanism works and for what to do when a new optimisation is built. Code comments in the forks and older session notes still name the old file.

## Goal
The final app only runs the extensions it ships with: the VM's built-in extensions and the extensions of the three offline galleries (PenguinMod, TurboWarp, SharkPool; the list is `src/extension-support/shipped-extensions.json` in the VM fork and the table below). Importing other extensions is impossible. Every shipped extension is integrated as much as possible into the engine's optimisations: the ones already present (sections 39–42 sensing cache, 44–45 compile-time folding, 62 list lookup tables, 63 hats checked only when their answer can change) and the planned ones listed under the headings of `docs/EXTENSION-RISKS.md`. Blocks may change behaviour, be merged or be removed if that lets them be optimised.

## Rules
- **Planned optimisations (was step 7):** whenever one of the optimisations planned under the headings of `docs/EXTENSION-RISKS.md` is built, give the shipped extensions what it needs, using the inventory (`block-inventory.json`, "Block inventory" below): what each block writes (parallel blocks, automatic parallel clones), hidden state registered with the engine (rewind, deterministic mode), page-dependent parts split off (engine in a worker), answer types (typed variables, type tracking). Column 7 of the table is this rule (? = not decided yet).
- Speed changes: measure before and after with `bench\bench.mjs` (only the affected projects, `--runs 3`), and show that results are identical with an equality test like `bench\edgehats-check.mjs` or `bench\list-lookup-eq.js`.
- Every engine or compiler change (optimisations, direct calls, extension fixes): run `bench\block-eq.mjs all <label>` ("Equality test for every block" below) on the new build; it must give no differences except the listed expected ones. A new switch that turns the change off goes into its `old` mode.
- An extension that can't be integrated (embeds web pages, needs online servers, ...): ask the user whether to keep it as it is or remove it.
- When a change alters how an extension reaches into the engine, update this file (the table and the section describing that mechanism) and `docs/EXTENSION-RISKS.md`.

## How loading works (sections 105, 108–110)
- Only built-in extensions load; since section 110 nothing loads from an address. The gallery extensions are built into the VM (sections 108–109, next heading); `loadExtensionURL` takes a built-in ID or a moved extension's old gallery address (`moved-gallery-extensions.json`) and refuses everything else ("Unknown extension"). Removed in section 110: `shipped-extensions.json` (section 105's list of gallery addresses; the local `list-shipped-extensions.mjs` that wrote it is obsolete), fetching and hashing extension scripts, the unsandboxed script loader (only `createUnsandboxedExtensionAPI` stays), the worker service methods, the security manager's `getSandboxMode` / `canLoadExtensionFromProject` / `rewriteExtensionURL` / `shouldUseLocal` and the editor's "load extension" prompt, the ScratchX layer, and in the packager the address baking, the "bake extensions" option and the security manager of packaged pages.
- Projects, sprites and copied blocks name extensions by ID only: stored addresses are ignored and not saved; an ID that is not built in stops the project from loading ("Unknown extension").
- Packager: a packaged game holds the scaffolding plus only the chunks of its project's gallery extensions (`scaffolding/extensions-min|extensions-full/ext-<ID>.js`, pushed into `pmDesktopScaffoldingChunks` before the game starts, so it never fetches one); stored `extensionURLs` are dropped. The app's old guessed table (`/__extension-ids__.json`) is gone since section 105.
- Gallery "Open Extension" messages are accepted only from the three gallery pages the app serves itself (exact origins); they name gallery addresses, which `loadExtensionURL` maps to the built-in.

## Pure blocks compiled directly (step 4, section 118)
- **Cost found:** a compiled extension reporter went through `executeInCompatibilityLayer` (a generator call with thread-status checks; it also makes the whole script a generator) and then the extension manager's wrapper (converts the arguments by their declared type, every call). Benchmark project 13 (a loop of 200,000 × 5 TurboWarp Bitwise calls per frame): 80.4 ms of work per frame, about 80 ns per call.
- **How:** VM `src/extension-support/pure-blocks.json` lists the inventory's pure reporters and Booleans without compiler code (`"<ID>_<opcode>": "<answer type>"`; `desktop_block_inventory.js` checks it matches the inventory: after changing a `pure`, `compiled` or `answer` there, make it again from the inventory). `extension-manager.js` gives each non-dynamic block function `pmDirect` (`call` without the wrapper, `argumentTypes()`, `normalize`). `irgen.js` `getPureExtensionAnswer`: such a block is a `compat` node with `pure` = its answer type and does not make the script yield. `jsgen.js` `descendPureExtensionBlock`: a direct call with the arguments object the wrapper would pass on (same values, same order, `mutation` included); conversions are left out where the input's type already matches and done at compile time for fixed values; answer types number (may be NaN) and boolean are given to the compiler, text stays unknown (the compiler's true/false test for known text differs from Scratch's for "" and "FALSE"); with every input fixed the block runs once at compile time and its answer replaces the call (`foldPureExtensionBlock`, same limits as section 44: no NaN, infinity, -0 or objects). `edge-hats.js` (section 63): these blocks and extension menus (shadow blocks with fixed fields) may be in a skippable "when" condition. Switches (tests only): `runtime.pmNoPureExtensionCalls`, `runtime.pmNoConstantFolding`.
- **Measured:** project 13 work 80.4 → 4.5 ms per frame; project 14 (2,000 clones × 4 "when" hats using Bitwise blocks) 14.3 → 1.05 ms.
