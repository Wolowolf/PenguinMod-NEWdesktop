# EXTENSION-INTEGRATION.md — how the shipped extensions are integrated into the engine

Was `EXTENSION-ROADMAP.md` until Session 128: the plan (steps 1–6, Sessions 105–128) is finished, and this file is now the reference for how each mechanism works and for what to do when a new optimisation is built. Code comments in the forks and older session notes still name the old file.

## Goal
The final app only runs the extensions it ships with: the VM's built-in extensions and the extensions of the three offline galleries (PenguinMod, TurboWarp, SharkPool; the list is `src/extension-support/shipped-extensions.json` in the VM fork and the table below). Importing other extensions is impossible. Every shipped extension is integrated as much as possible into the engine's optimisations: the ones already present (sections 39–42 sensing cache, 44–45 compile-time folding, 62 list lookup tables, 63 hats checked only when their answer can change) and the planned ones listed under the headings of `docs/EXTENSION-RISKS.md`. Blocks may change behaviour, be merged or be removed if that lets them be optimised.

## Rules
- **Planned optimisations (was step 7):** whenever one of the optimisations planned under the headings of `docs/EXTENSION-RISKS.md` is built, give the shipped extensions what it needs, using the inventory (`block-inventory.json`, "Block inventory" below): what each block writes (parallel blocks, automatic parallel clones), hidden state registered with the engine (rewind, deterministic mode), page-dependent parts split off (engine in a worker), answer types (typed variables, type tracking). Column 7 of the table is this rule, filled in for every extension in Session 166 (key above the table): plan an optimisation from it instead of re-reading the extensions, and update the cells of the extensions it changes.
- Speed changes: measure before and after with `bench\bench.mjs` (only the affected projects, `--runs 3`), and show that results are identical with an equality test like `bench\edgehats-check.mjs` or `bench\list-lookup-eq.js`.
- Every engine or compiler change (optimisations, direct calls, extension fixes): run `bench\block-eq.mjs auto <label>` ("Equality test for every block" below) on the new build: it runs only what the change needs (or says it is not needed); it must give no differences except the listed expected ones. It also picks the page test (Session 150). Run `all` or `page` by hand only before moving to newer upstream code; when `auto` chooses more than the change can affect (e.g. everything for one extension's file), find out why before running it. A new switch that turns the change off goes into its `old` mode.
- An extension that can't be integrated (embeds web pages, needs online servers, ...): ask the user whether to keep it as it is or remove it.
- **Engine contacts (section 153):** after changing any extension's code, or the engine parts it uses, run `node test/unit/desktop_engine_contacts.js` in the VM ("Engine contacts" below). A new contact (random numbers, clock, page, engine internals) goes through the engine's entry point for it once that exists; otherwise, when it is meant, remake the list with `--write` and commit it with the change. Entry points so far (section 154): random numbers `runtime.pmRandom()` instead of `Math.random()`, wall-clock time `runtime.pmDateNow()` instead of `Date.now()` (and `new Date(runtime.pmDateNow())` instead of `new Date()`), the monotonic clock `runtime.pmPerfNow()` instead of `performance.now()`; since section 156 timers: `runtime.pmSetTimeout` / `pmClearTimeout` / `pmSetInterval` / `pmClearInterval` / `pmRequestAnimationFrame` / `pmCancelAnimationFrame` for every timer whose callback changes what blocks answer or do (a timer that only manages the page, the network, a login or the editor, or guards against a hang, stays on the browser's); since section 159 the page's dialogs, localStorage and window / document event listeners: `runtime.pmPage.alert` / `confirm` / `prompt`, `storageGet` / `storageSet` / `storageRemove` / `isLocalStorage`, `addEventListener` / `removeEventListener('window' | 'document', …)` ("One door to the page" below); gallery code reaches them as `Scratch.vm.runtime.…`, compiler helpers as `runtime.…` / `target.runtime.…`.
- When a change alters how an extension reaches into the engine, update this file (the table and the section describing that mechanism) and `docs/EXTENSION-RISKS.md`.

## How loading works (sections 105, 108–110)
- Only built-in extensions load; since section 110 nothing loads from an address. The gallery extensions are built into the VM (sections 108–109, next heading); `loadExtensionURL` takes a built-in ID or a moved extension's old gallery address (`moved-gallery-extensions.json`) and refuses everything else ("Unknown extension"). Removed in section 110: `shipped-extensions.json` (section 105's list of gallery addresses; the local `list-shipped-extensions.mjs` that wrote it is obsolete), fetching and hashing extension scripts, the unsandboxed script loader (its API function stayed until section 142, which moved what is left of it into `desktop-gallery-extension.js`), the worker service methods (section 142: the whole worker message system `src/dispatch` too; extensions are plain objects in `_loadedExtensions`, called directly), the security manager's `getSandboxMode` / `canLoadExtensionFromProject` / `rewriteExtensionURL` / `shouldUseLocal` and the editor's "load extension" prompt, the ScratchX layer, and in the packager the address baking, the "bake extensions" option and the security manager of packaged pages.
- Projects, sprites and copied blocks name extensions by ID only: stored addresses are ignored and not saved; an ID that is not built in stops the project from loading ("Unknown extension").
- Packager: a packaged game holds the scaffolding plus only the chunks of its project's gallery extensions (`scaffolding/extensions-min|extensions-full/ext-<ID>.js`, pushed into `pmDesktopScaffoldingChunks` before the game starts, so it never fetches one); stored `extensionURLs` are dropped. The app's old guessed table (`/__extension-ids__.json`) is gone since section 105.
- Gallery "Open Extension" messages are accepted only from the three gallery pages the app serves itself (exact origins); they name gallery addresses, which `loadExtensionURL` maps to the built-in.

## Block inventory (step 2, sections 106–107)
- **File:** VM `src/extension-support/block-inventory.json`, one entry per inventoried extension ID: `source` (gallery extensions only: its file, relative to the local test's `galleries` folder, e.g. `SharkPools-Extensions/extension-code/Scenes.js`; for one moved into the VM, its VM file, e.g. `src/extensions/penguinmod_gallery/Gen1x/iris-text.js`, which the test runs the same way), `note` (optional, about the whole extension), `replaces` (engine functions it replaces or adds: the engine is compared before and after the extension loads, then checked in its code) and `blocks`, one line per block: `type` (block type), `pure` (reporter, Boolean or hat whose answer depends only on its inputs and which changes nothing: may be folded, cached or skipped), `reads` / `writes` (engine state, tags below), `time` (depends on the clock or frame count), `random`, `waits` (can last more than one frame: promise, yield, timer), `hiddenState` (keeps its own state between calls, outside the project), `page` (needs the page: DOM, window, navigator, network, a page canvas), `answer` (`number`, `string`, `boolean`, `object`, `array`, `any`; `null` for blocks without an answer), `compiled` (already has compiler code: `getCompileInfo` or the compiler itself), `direct` (optional, only ever `true`: code read, called without the check after a direct call, section 132, "Ordinary blocks called directly" below), `note` (optional: what later steps must know).

## Pure blocks compiled directly (step 4, section 118)
- **Cost found:** a compiled extension reporter went through `executeInCompatibilityLayer` (a generator call with thread-status checks; it also makes the whole script a generator) and then the extension manager's wrapper (converts the arguments by their declared type, every call). Benchmark project 13 (a loop of 200,000 × 5 TurboWarp Bitwise calls per frame): 80.4 ms of work per frame, about 80 ns per call.
- **How:** VM `src/extension-support/pure-blocks.json` lists the inventory's pure reporters and Booleans without compiler code (`"<ID>_<opcode>": "<answer type>"`; `desktop_block_inventory.js` checks it matches the inventory: after changing a `pure`, `compiled` or `answer` there, make it again from the inventory). `extension-manager.js` gives each non-dynamic block function `pmDirect` (`call` without the wrapper, `argumentTypes()`, `normalize`). `irgen.js` `getPureExtensionAnswer`: such a block is a `compat` node with `pure` = its answer type and does not make the script yield. `jsgen.js` `descendPureExtensionBlock`: a direct call with the arguments object the wrapper would pass on (same values, same order, `mutation` included); conversions are left out where the input's type already matches and done at compile time for fixed values; answer types number (may be NaN) and boolean are given to the compiler, text stays unknown (the compiler's true/false test for known text differs from Scratch's for "" and "FALSE"); with every input fixed the block runs once at compile time and its answer replaces the call (`foldPureExtensionBlock`, same limits as section 44: no NaN, infinity, -0 or objects). `edge-hats.js` (section 63): these blocks and extension menus (shadow blocks with fixed fields) may be in a skippable "when" condition. ## Hidden state (section 158, Session 164)
- **Why:** a later rewind, save state or undo while running must capture the whole running project, also what extensions keep for themselves (timers, animations, physics, 3D and GPU data), not only sprites, variables and lists.
- **How:** an extension calls `runtime.pmRegisterState(<its ID>, {save, restore, notRestored})`. `save()` returns its state as plain data, without page objects or sprites (it may hand over live objects: the engine copies everything at once with `structuredClone`, which keeps shared objects shared and refuses functions); `restore(state, time)` gets a fresh copy and puts it back: sprites looked up by the ID the state is kept under (missing ones dropped), saved clock readings plus `time.dateShift` (`pmDateNow`) or `time.perfShift` (`pmPerfNow`), then the signals the extension's hats wait for (`pmEdgeHatsChanged`). What restore cannot rebuild from data stays as it is and is listed in `notRestored` (`runtime.pmStateInfo()` returns those lists). `runtime.pmSaveStates()` / `pmRestoreStates(snapshot)` do all at once. Nothing calls them during normal running; a feature that does is opt-in.
- **Covered:** the project timer (`clock`), Extra Timers, Animations, Beat Sync. ## One door to the page (section 159, Session 165)
- **Why:** an engine that later runs in a background worker has no page (no `document`, `window`, dialogs, storage, page events or stage canvas). When every extension reaches the page through one object, that engine needs only a stand-in for this object, not changes to 76 extensions.
- **How:** `runtime.pmPage` (VM `src/engine/page-door.js`, made in the `Runtime` constructor). Each function calls the page function it stands for with the same arguments and returns its answer, so nothing changes while the engine is on the page. Gallery code reaches it as `Scratch.vm.runtime.pmPage.…` (header note "section 159" in each moved file), built-in extensions as `this.runtime.pmPage` / `runtime.pmPage` (line notes). The leak checker counts its uses as entry points (`--report`: `pmPage.<function>`), not as page contacts.
- **Groups, by what a worker stand-in has to do:**
  - *Messages* (plain data in and out; a stand-in sends a message to the page and gets the answer; dialogs and storage answer at once on the page, so in a worker the block would wait for it, e.g. with `Atomics.wait` or by making the block wait like a promise). Done: dialogs `alert(…)`, `confirm(…)`, `prompt(…)`; localStorage `storageGet(key)`, `storageSet(key, value)`, `storageRemove(key)`, `isLocalStorage(area)` (a storage event's `storageArea`; without a localStorage the getter gives `null` and set / remove do nothing, as Iris Text's own check did; the app always has one). Planned: page facts (window and screen size, `devicePixelRatio`, `document.hidden` / `visibilityState` / `hasFocus`, fullscreen and pointer lock state, title, location), page actions (`open`, close / move / resize the window, fullscreen and pointer lock on and off, `history`), device access (`navigator.clipboard`, `getGamepads`, `vibrate`, `getBattery`, `wakeLock`, `geolocation`, `requestMIDIAccess`; mostly promises already).
  - *Page events*. Done: `addEventListener(target, type, listener, options)` / `removeEventListener(…)`, target `'window'` or `'document'`. On the page the listener gets the real event; a stand-in would listen on the page and send a plain copy of the event's fields. Listeners that call the event's methods or read page objects from it need the page side: Clipboard (`clipboardData` in copy and paste), My Blocks+ (its error listener), Pen+ (`message` from its iframe), MIDI (visualizer dragging).
  - *Stage canvas* (`renderer.canvas` 9 extensions, `renderer.gl` 3). Planned: a function that gives the stage canvas (in a worker: the renderer's OffscreenCanvas) and its size and place on the page (a page fact, as above).
  - *Images and media* (`Image` 14, `Audio`, audio contexts, `MediaRecorder`, `navigator.mediaDevices` 6, speech recognition, WebRTC). Planned: images loaded through the door (in a worker `fetch` + `createImageBitmap`); sound, camera, microphone and connections stay on the page and are driven by messages.
  - *Page elements* (`document.createElement` 41, `document.body` 20, `querySelector` 11, `getElementById` 7, observers, fonts, styles). Planned last: the hardest, a worker has no elements at all; an extension's element code would move into a page-side part that the door talks to (an overlay over the stage, owned by the door, for the extensions that draw over it).
- **Done (31 extensions, 78 calls; page contacts 848 → 768 uses, 76 → 70 extensions, 117 → 105 kinds):** no page contacts left: Sound Waves, ShovelUtils, Keys+ V2, Device Motion, Looks+, Local Storage; some left: Prism, Events Expansion, Resolution, Beat Sync, Iris Text, Lighting, MIDI, Dictation, Video Sharing, Hyper Sense V2, MIDI Tools, My Blocks+, Scenes, Sharktilities, Sprite Effects V2, Tune Shark V3, Window Controls, Wake Lock, Video, Simple 3D, Clipboard, CloudLink, Sensing+, Pen+, Pointerlock.
