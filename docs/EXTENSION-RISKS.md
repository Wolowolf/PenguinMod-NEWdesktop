# EXTENSION-RISKS.md — which extensions a change could disturb

Used by the CLAUDE.md "Extensions" rule: Grep the area (heading) or the extension's name, then decide whether to test. A name here means the extension's code reaches into that part of the engine, and how; it does not mean it will break. Galleries: `pm` PenguinMod, `tw` TurboWarp, `sp` SharkPool; built-in: `vm`. Names are file names (pm/tw: path without `.js`, sp: file name, vm: extension ID).

**How this was made (Session 62, 2026-10-10; Session 66, 2026-10-11, Sessions 67–68, 2026-10-11, removed extensions taken out; Session 85, 2026-10-15, web-page-only extensions removed; Session 90, 2026-10-16, 9 extensions using services without permission removed; Session 105, 2026-10-20, Custom Styles and Close Control (removed in Session 104) taken out), only extensions still present (124; since section 105 these are the only ones that can load, see `docs/EXTENSION-INTEGRATION.md`):** vm 17 = every extension registered in the VM's `extension-manager.js`, all in the extension library (the 11 hidden ones were removed in Session 68); pm 27 = the 25 in `src/lib/extensions.js` + 2 the extension library lists from the PenguinMod gallery folder (`SharkPool/Sound-Waves`, `SharkPool/Tile-Grids`); tw 48 = `extensions/extensions.json`; sp 32 = `Gallery Files/Extension-Keys.json` without `Example` and deprecated ones (what the Extensions tab lists, `galleries.js`). ## Already overridden by this app (facts, not risks)
- Section 21 forces `maxClones: Infinity`, `miscLimits: false`, `fencing: false`, `dangerousOptimizations: true` (`PM_ALWAYS_ON` in the VM's `runtime.js`, re-applied on every `setRuntimeOptions`) and high quality pen (`setUseHighQualityRender` ignores its argument). So these blocks set nothing: tw `runtime-options` (clone limit, fencing, misc limits, high quality pen), sp `Scenes` (restores fencing / misc limits), vm `pmCamera` (switches fencing off at load). They still read back the forced values. `disableOffscreenRendering`, `disableDirectionClamping`, warp timer, turbo mode and frame rate still change.
- Interpolation is gone (`vm.setInterpolation` and `runtime.setInterpolation` are empty, sections 21 and 41): tw `runtime-options`' interpolation switch and sp `Scenes` do nothing there; sp `Particle-Engine` (and `Scenes`) reads `runtime.interpolationEnabled`, which stays off.
- Since sections 108–109 all 107 gallery extensions are VM built-ins (`src/extensions/{penguinmod,turbowarp,sharkpool}_gallery/<name>.js`, same code except where marked "Desktop fork"; names here unchanged); since section 110 each is a chunk of its own, so they load asynchronously, and nothing loads from an address. Loading one no longer sets the runtime's `customExtensions` communication flag, so with privacy enforced the renderer keeps its private-skin access as with built-ins (before, any gallery extension turned it off: e.g. the webcam picture was left out of "touching color").
- vm `pmMotionExpansion` calls the renderer's `getFencedPositionOfDrawable` itself, so its own fencing still works (reasoned, not run).

## No extension at risk
Strong GPU · higher memory limit · Wasm for a few slow parts · heavy jobs in workers · GPU calculations · tilemaps, GPU particles, physics engine, 3D, saving, multiplayer, text scripting, performance hints (new features; only clash if they copy an extension's block names or extension ID).

## Compiler
Remembered results · work before the game runs · type tracking · inlining custom blocks · strict mode · pre-compiled scripts · compiling to Wasm.
- Register compiled blocks (`getCompileInfo` / `registerCompiledExtensionBlocks`, own IR / JS kinds): vm `jwProto`, `pmControlsExpansion`, `pmOperatorsExpansion` · pm `Div/divVecQuat`, `Gen1x/iris-text` · sp `Temporary-Variables`, `My-Blocks-Plus`, `Extra-Controls` (section 121). Several write `compiler.source` directly. None registers an `op.*` kind, so sections 44–45 folding stays on with all of them (`pmOperatorsExpansion`'s 11 kinds are folded since section 45).
- Pure extension blocks called directly (section 118, roadmap step 4): the 275 blocks in VM `pure-blocks.json` skip the compatibility layer and the extension manager's wrapper; their function is found through `runtime.getOpcodeFunction(opcode).pmDirect` when the script is compiled and started. An extension that replaced a pure block's function (in `runtime._primitives`) without keeping `pmDirect` would make scripts compiled afterwards use the old path (irgen checks it), but scripts compiled before would fail when started again; no shipped extension does that (sp `My-Blocks-Plus` wrapped `getOpcodeFunction` for `procedures_call` until section 121). A block wrongly marked pure would be folded or skipped in hats: the inventory test and `benchpure-eq.mjs` guard that.
- Ordinary extension blocks called directly (section 130): every other non-dynamic extension command, reporter and Boolean is called through `runtime.getOpcodeFunction(opcode).pmDirect` (looked up when the script is compiled and started, like section 118) followed by a check that finishes promises, yields and stops exactly as the compatibility layer does (`docs/EXTENSION-INTEGRATION.md` "Ordinary blocks called directly"). The same caveat as above: an extension replacing a block's function without `pmDirect` after scripts were compiled would break them when started again (no shipped extension touches `runtime._primitives`). Hats and dynamic blocks still use the compatibility layer (branches: section 152, below) (no shipped block is dynamic, Session 132: `isDynamic` is only set on whole extensions, for palette refreshes; blocks that answer through a promise take this guarded call). Answers stay of unknown type to the compiler. Plain calls (sections 132–137, 141, 144): the blocks in VM `direct-blocks.json` (inventory `"direct": true`, code read: they never wait, yield, change a thread's status or read stack frames; group 1: tw `qxsck/var-and-list`, `Lily/ListTools`; group 2: tw `Lily/ClonesPlus` without its hat, stop and delete blocks, sp `Variables-Expanded` without its hat; group 3: pm `ObviousAlexC/3DMath`, all blocks; group 4: tw `obviousAlexC/penPlus`; group 5: tw `Xeltalliv/simple3D`; group 6: 461 blocks of 44 more extensions; group 7: 425 blocks of 48 more extensions (Tune Shark V3's start "when sound []" threads with `_pushThread`); group 8: 341 page blocks of 47 extensions that never wait (DOM, canvases, window, storage, network objects; promises they start are never returned); group 9: 17 blocks of 5 extensions whose inventory says they write threads but that start scripts only with `_pushThread` (Tune Shark V3's sound blocks, Extra Controls "call [] to run"), only later (ShovelUtils "import project") or not at all (MIDI Tools), or only mark other threads' tweens cancelled (Tween), lists in `docs/EXTENSION-INTEGRATION.md` Groups) are called without the check and don't make their script a generator. A change to one of these blocks that makes it wait, yield, stop or restart a script, or read stack frames, must remove its `direct` (its script would otherwise not be able to pause: the wait would be lost). Restarting the calling script itself is not noticed by the check either (`_restartThread` replaces the thread object and leaves the old one running), so it is the same on every path; but restarting another script can stop the caller through sp `Extra-Controls`' restart hook (it stops the thread its "step through blocks while" started), which only the check notices (Session 152): blocks that restart scripts (broadcasts, Events Expansion's broadcast and "force run") stay guarded, and since section 148 so do the 26 marked blocks that start a hat at once ("force hat" can make any hat restart: costume switches, clones, stage, canvas and render size, runtime options, username, fonts). A change that makes a plain block start a hat, also through an event another extension listens to, must remove its `direct`; local `block-eq.mjs` `PROBE=1` lists the hats plain blocks start.
- Core blocks compiled to inline code (section 138): 48 core reporters, Booleans and commands that used the compatibility layer (list in `docs/SECTIONS.md` 138) no longer call their function in `runtime._primitives`; an extension that replaced one of those functions would change interpreted scripts only (no shipped extension touches `runtime._primitives`). Extension blocks inside their inputs are compiled and called as before. Their node kinds (`op.nand`, `sensing.isNumber`, `looks.stretch`, `motion.changeXY`, `list.reverse`, …) are not registered by any extension. Local `bench\core-eq.mjs` compares them compiled, with `runtime.pmNoCoreInline` and interpreted.
- Extension branch and loop blocks (section 152): every C-shaped extension block without compiler code of its own (26) skips the compatibility layer: 8 Extra Controls blocks (if, else, wait or until, wait until changed, repeat or until, repeat for secs (or until), spayed loop) have inline helpers that copy their function (a change to one of them in `Extra-Controls.js` must be made in `jsexecute.js` `pmBranchInline_<opcode>` too, or the two paths differ); the other 18 are called through `pmDirect` with a check that does what `executeInCompatibilityLayer` does (same caveat as section 130 for an extension replacing a block's function). The generated loop around them is unchanged. Extra Controls' "if" / "else" IDs are read through `runtime.ext_SPadvControl.pmConditionStorage`. `docs/EXTENSION-INTEGRATION.md` "Branch and loop blocks without the compatibility layer".
- Where the interpreter still runs (Session 142, read in the engine code): monitors (`_pushThread` never compiles `updateMonitor` threads), scripts the compiler cannot handle (the fallback; it must stay, or such scripts would stop working), threads extensions make by hand without `tryCompile` (sp `Extra-Controls` "run [reversed / randomized / …]" and "async", vm `pmEventsExpansion`'s `evaluateBlock`), and the compiler switched off in the settings. Monitors measured (local `bench\monitor-cost.mjs`, bench project 21: 200 visible monitors, two runs each): 0.32 ms per frame in all, about 0.15 ms of it handing the values to the monitors (`requestUpdateMonitor`, which compiling would not change) and about 0.17 ms making and interpreting their threads; compiling could save only part of the latter (the threads are still made every frame), well under 0.1 ms even with 200 monitors and about 0.005 ms for a usual 5–10. Not done (user, Session 142): too small a gain for the risk of wrong monitor values; the hand-made threads only run when those blocks are used.
- Equality for every block (Session 131): local `bench\block-eq.mjs` runs every block of every shipped extension (3 input sets) compiled, interpreted and with sections 118, 127, 128 and 130 switched off, and lists what differs; rerun it after any change in this group, with `auto` (Session 146: only the extensions and modes the change needs; `docs/EXTENSION-INTEGRATION.md` "Equality test for every block"); the page blocks with `page` (Session 148: stand-ins for the page's features, also a guarded mode), after changes to them or to the direct calls.
- Compiling custom block calls (section 121): sp `My-Blocks-Plus` compiles calls with custom branch inputs through `runtime.pmProcedureCallIrHooks` / `pmProcedureCallJsHooks` (the usual call: `descendDefaultProcedureCall`). No shipped extension replaces a compiler class function any more (Temporary Variables, My Blocks+ and Extra Controls did until section 121).
- Variable type tracking (section 151): the compiler forgets what it knew about variables' types after every extension block that is not pure, so any extension may set variables; an extension block that wrote a variable from its own compiled code (`setExtensionJs`) would have to call `compiler.resetVariableInputs()` itself (none of the 8 that have such code writes one). Typed text reaches extension blocks as text ("9", as interpreted), not as the number 9; the conversion by argument type is the same, done when compiling for fixed inputs. A variable set to typed number text still holds a number in compiled scripts ("9" → 9), so an extension that checks `typeof` of a variable's value sees a number there and text when interpreted.

## Threads and scripts
Parallel blocks · automatic parallel clones · debugger · event-driven hats.
- Scheduler hooks (section 119): sp `Messages-Plus` adds threads to a broadcast's through the `HATS_STARTED` event (vm `pmEventsExpansion` listens to it too; the two run in the order the extensions loaded) and decides restarts through `runtime.pmRestartThreadHooks` (it wrapped `startHats` and `_restartThread` before). Editor value bubbles: pm `ObviousAlexC/3DMath` through `runtime.pmVisualReportHooks`.
- Block-data hooks (section 121): blocks a sprite lacks are looked up in other sprites through `runtime.pmForeignBlockHooks` (sp `Extra-Controls` for "as sprite do" / "get from sprite", `My-Blocks-Plus` for global custom blocks; asked only on a miss, so a sprite's own block always wins), procedures through `pmForeignProcedureHooks` (`My-Blocks-Plus`; cached like the sprite's own, `pmResetCacheHooks` resets the other sprites when a compiled global changes), input lists through `pmBlockInputsHooks` (`My-Blocks-Plus` drops custom branch inputs). No shipped extension replaces a scheduler, Blocks or sequencer function any more.
- Stack frame objects are reused (`_StackFrame` free list; `reset()` clears only the engine's own fields): a field an extension puts on a frame object can reach an unrelated thread later (sp `Extra-Controls` kept its thread arguments on `stackFrames[0]` until section 131). - Make threads by hand (`_pushThread`, `runtime.threads.push`): vm `pmEventsExpansion` · sp `Tune-Shark-V3`.
- Change thread fields (status, target, stack frames): sp `Extra-Controls`, `My-Blocks-Plus`, `Sharktilities` · tw `godslayerakp/ws` (sets status done) · vm `jgTween` (walks `runtime.threads`), `pmControlsExpansion` (`_restartThread` in compiled code).
- Edge-activated extension hats (section 127, roadmap step 6a): checked only when their answer can change, through `pmEdgeHat` in their block info and `runtime.pmEdgeHatsChanged` signals (`docs/EXTENSION-INTEGRATION.md` "Hats checked when their answer can change"): vm `videoSensing` (while it has camera frames), `pmEventsExpansion` (`whenTrueFalse`, `whenKeyAction`: inputs, keyboard) · pm `Gen1x/beat_sync` (while syncing), `steve0greatness/timers` (while a timer runs), `electricfuzzball_pm/MIDI` (MIDI messages; its hats clear their note flag and signal when they do) · tw `lab/face-sensing` (while a face is detected), `Lily/lmsutils` (inputs, keyboard), `Lily/ClonesPlus` (a variable), `cloudlink` (while connected) · sp `MIDI-Tools` (played notes). A missing signal when that state changes would make a hat fire late or not at all: code that changes what these hats read must signal. vm `jwProto`'s label hat is not edge-activated since section 127. Hats their extension starts every frame (not edge-activated, section 128, roadmap step 6b): skipped while their last check answered false and nothing they read changed (`pmEdgeHat` on a level hat, `docs/EXTENSION-INTEGRATION.md` "Level hats skipped while false"): vm `pmEventsExpansion` ("while <>", "when [] is changed": inputs; "while key pressed": keyboard) · sp `Hyper-Sense-V2` (key hat: keys, every frame while one is held), `KeysPlusV2` (mouse, key, keys, keybind hats: keys, mouse buttons, keybinds, tags), `Sharktilities` ("when [] is changed": inputs), `Variables-Expanded` (button hat: buttons, every frame while one is down). The same rule: code that changes what they read must signal. Events Expansion's "every [] frames" and "every other frame" are still checked on every (second) frame. Most other extension hats are started from events with `startHats`.
- Section 63 (hats checked only when their answer can change): applies to the built-in "when <>" and "when timer >" with conditions made of numbers, text, variables, x/y/direction, plain operators and (section 118) the pure extension blocks of `pure-blocks.json` with their menus, and (section 127) to extension hats with `pmEdgeHat` whose inputs qualify the same way; conditions with other extension blocks are checked every frame as before.
